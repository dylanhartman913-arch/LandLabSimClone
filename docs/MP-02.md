# MP-02 — Shared authoritative simulation

Both seats enter the existing game from **Enter shared homestead** in the lobby.
The server initializes one Front Range greenfield scenario on Standard, seed 2026,
with two simulated adult residents and the existing instructions tutorial. Joining
a human seat does not add household labor. Single-player remains the root game.

## Authority and supported controls

The room runs the engine and owns cash, stocks, instance IDs, costs, refunds,
scenario settings and time. Authenticated intention requests pass strict schemas;
raw replay insert/delete, supplied IDs, cash deltas, prebuilt placements, settings,
time stamps, non-finite values and unknown fields are rejected. Each command batch
and day tick runs synchronously in Node's event queue, with no await between
validation against current state and commit. A failed batch leaves its game and
revision unchanged. Revisions advance for accepted edits and shared control changes.

Both players can place/buy or DIY, move, remove, copy/paste, build local plans,
set system priorities and provider links, buy supplies and standing orders, book
construction crews, and change work priorities/caps, auto-gather and emergency
construction. Recovery routes are computed again on the server when booked, so
client-calculated instance IDs cannot select the wrong new project. Experimental
operations pass through engine checks and remain disabled by this fixed scenario.
Players cannot add/remove simulated residents. Tutorial inspection actions are
shared; skipping the tutorial is disabled for this room.

The browser store forwards intentions without applying optimistic engine edits.
Server snapshots update gameplay fields while camera, selection, local build-plan
ghosts and open panels remain local. Browser ticks, autosaves, local game loading,
undo/redo, new-game replacement and save/settings panels are disabled in rooms.
Read-only planning remains available.

## Clock and connection behavior

The server advances at one simulated day per second after both connected players
choose **Ready to run**. Either player's Pause clears both Ready states. A shared
fixed policy pauses for an Act now survival alert, hardship, warned risk event,
completed construction or harvest. Both see the same reason and must agree again.
Preferences in an individual browser do not affect this policy.

Snapshots use authenticated HTTP streaming (newline-delimited JSON), with separate
JSON POSTs for commands and controls. This uses Node HTTP and browser Fetch already
available in the project, avoiding an additional WebSocket dependency. It meets
MP-02 synchronization criteria; it is a deliberate change from the roadmap's
proposed WebSocket transport. Credentials travel in Authorization headers, never
in invite URLs. A second connection using the same credential is refused explicitly.

Clients acknowledge liveness every two seconds. A closed stream pauses immediately;
a missing heartbeat pauses after seven seconds, checked once per second. A slow
stream whose queued data exceeds 2 MB is closed and pauses the room. Manual
Reconnect works while this page retains its seat token; refresh seat recovery,
automatic retries and durable progress are MP-03. Rooms remain in memory and are
lost on service restart or free-host spin-down.

## Bounds and history

The initial snapshot contains at most 90 daily ledgers. Later updates send only
the latest daily ledger, merged into that history in the browser. Updates also
include up to 100 recent events and 12 season/year reports, without the
accumulating action log or credentials. Opening
the needs checklist fetches the server's retained history separately (up to the
engine's 730-day retention) for annual/worst-week inspection. Later snapshots merge
new ledgers into that local history cache. History failures close the checklist
and show an error, rather than silently presenting an incomplete annual view.

Limits: 100 rooms, two seats each, 500 placed systems per room, 20 authenticated
requests per seat per second, 50 intentions per atomic request, 32 KiB command
bodies, 2 KiB other JSON bodies. Each seat rejects reuse of its last 1,000 accepted
request IDs; durable/reconnect-safe outcome handling belongs to MP-03. The schema
validator is the existing project Zod dependency, now declared directly by the
server workspace; no new library was introduced.

## Verification

Authority tests cover competing spending, stale placement conflicts, atomic
rollback, forged commands, both players' edits, server-only ticking, Ready/manual/
alert pauses, duplicate requests, and bounded payloads on an actual cabin design
after 730 simulated days. Real HTTP tests cover credential checks, duplicate
connections, stream convergence and missing-heartbeat pauses. Browser-store tests
check that mutations leave local gameplay untouched and local replacement paths
are blocked. Existing tests remain intact.

The production browser suite uses isolated profiles to create/join/full/invalid
rooms and to build from both seats, purchase through the market UI, change work,
compare complete gameplay state, check independent selection/camera, verify local
tick rejection, agree to run, pause, and close a teammate's connection. Run:

```sh
npm run typecheck
npm run lint
npm test -- --maxWorkers=2
npm run build:hosted
npm run test:multiplayer
MP_BASE_URL=https://terra-homestead.onrender.com npm run test:multiplayer
```

Hosting remains the existing free service in My Workspace, with manual deployment.
No new paid infrastructure is required for MP-02. See [hosting details](MULTIPLAYER_HOSTING.md).

Local verification on October 26, 2026: the full unit suite passed 78 files /
870 tests. After the update-size optimization, the 13 authority/HTTP/store tests
passed again. Typecheck, lint, frontend/server production builds and diff checks
passed. Five existing single-player smoke, market and save browser tests passed.
The actual two-year cabin measured 8,758,234 bytes as full state, 1,108,881 bytes
for initial recent history, and 47,901 bytes for a regular update.
The final local production multiplayer suite passed both tests in 24.9 seconds,
including two consecutive shared days and merging incremental history. The shared
game screenshot was inspected for desktop layout and readable control states.
