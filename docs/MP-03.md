# MP-03 — Save and reconnect

Rooms commit state to atomic files before the server acknowledges or broadcasts a
revision. Refresh in the same browser tab reclaims its existing seat, loads current
state and resolves pending edits. Reconnecting never resumes time automatically.
Both players must choose Ready again.

## Durable commits and failure handling

`ROOM_DATA_DIR` is an absolute path. Local `npm start` defaults to the ignored
`tmp/multiplayer-rooms` directory. Render startup refuses to run without an explicit
data directory; production must point it inside the attached persistent disk.
The service remains single-instance. Synchronous validation, engine mutation and
file commit have no intervening await, so competing commands cannot spend a stale
balance or interleave writes.

Each file includes room ID/expiry, revision, fixed initialization, full retained game
state (including tutorial and ledgers), recent events/reports, reconnect credentials,
and each seat's accepted intention history, fingerprints and committed revisions.
Format, engine version, catalog SHA-256, initialization and a SHA-256 integrity
checksum are checked on load. Incompatible or corrupt files are refused with a
visible room error and are never replaced with a fresh game.

Writes create a mode-0600 temporary file in the same directory, flush its contents,
rename it over the room file, then flush the directory entry. Only then does the
new revision reach clients. Credentials are excluded from public room information,
stream snapshots, URLs and logs. Keep the volume and backups private.

A failed write rolls the in-memory room back to its last acknowledged checkpoint,
pauses time, clears both Ready states and broadcasts an explicit storage failure.
No candidate purchase or successful save is acknowledged. The room refuses further
edits until the owner repairs storage and restarts; readiness returns HTTP 503.
If rename succeeded but the directory flush failed, the on-disk commit may exist.
After restart, the retained request outcome resolves this ambiguity safely.
Expected filesystem errors take this explicit failure path; unexpected runtime
errors still terminate the process rather than claiming a healthy save.

Startup always restores rooms paused with both seats disconnected and not Ready,
regardless of the state before shutdown. Revisions remain monotonic across reloads.
The owner disconnecting does not destroy a room.

## Seat and command recovery

The guest token and pending intention envelopes are retained in this tab's
`sessionStorage`, separately for each room. Refresh recovers them automatically.
An invitation never contains the token and cannot reclaim an occupied seat. A
second live connection with the same token is explicitly rejected; automatic
retry waits for the old stream/heartbeat to clear. Closed streams pause immediately;
missing heartbeats pause after seven seconds, checked once per second.

The browser reconnects automatically with a one-to-eight-second backoff and also
provides Reconnect. It asks the authenticated request-outcome endpoint about each
pending ID before retrying an unknown request using the same ID and body. An
accepted retry returns its original committed revision plus the current snapshot,
without spending again or incrementing the revision. Reusing an ID for different
commands is rejected. IDs are scoped to the seat, durable, and never silently evicted.
Ready controls are deliberately not replayed. A network failure leaves pending
edits visible, and a browser-storage failure stops transmission before the edit.

Keep this tab open: closing it, clearing site data or using a different browser
loses its guest reconnect credential. Account-based/cross-device seat recovery is
outside MP-03. The server retains at most 10,000 accepted requests per seat,
50 intentions per request and 50 pending browser requests. Reaching a command limit
is an explicit rejection. Existing 32 KiB command/2 KiB other-body, 500-system,
20 POSTs/second/seat and 100-room limits remain.

Rooms expire seven days after creation, covering the October 31 competition target.
Expired rooms cannot be joined or reclaimed. Their files are retained on disk for
owner-managed recovery; no automatic deletion runs during judging. Room saves are
limited to 24 MiB each and 512 MiB total, leaving space on the 1 GB volume. Capacity
or disk failures stop saving visibly. Host usage and old files need review before
long-term operation. Engine ledgers retain their existing 730-day bound; snapshots
still send recent history only and fetch longer history separately.

## Hosting configuration

The checked-in `render.yaml` describes the existing `terra-homestead` web service
in My Workspace, one `0.5c-512mb` instance, a 1 GB disk at `/var/data`, and
`ROOM_DATA_DIR=/var/data/rooms`. The root remains the single-player game; shared
play is at `/?multiplayer`. Manual deploys remain enabled to avoid interrupting
active rooms on every documentation push. The existing service was created through
the connector, so editing this Blueprint alone does not apply it: reconcile the
Dashboard settings explicitly and record actual provisioning below.

The dashboard lists compute at $7/month. [Render pricing](https://render.com/pricing)
lists persistent disks at $0.25/GB/month. Baseline is therefore $7.25/month or
$14.50 for two months, within the owner's $20 total authorization before taxes or
usage overages. Do not enable paid autoscaling or add paid resources beyond that
budget. Review hosting before December 26, 2026; paid resources continue billing
until suspended/deprovisioned. [Disk deployment constraints](https://render.com/docs/disks)
mean a brief interruption on deployment; reconnect/reload is part of verification.

## Validation

- Server tests use real filesystem writes/reloads and HTTP streams: persisted day,
  tutorial/state, credentials and outcomes; simultaneous conflicting purchases;
  unauthorized commands/outcome reads; changed-body request-ID reuse; actual write
  failure and rollback; an uncertain post-rename failure; incompatible/corrupt saves.
- Browser tests preserve the original invite, shared gameplay, clock and view checks,
  and add refresh seat recovery, offline/online recovery with a teammate's edit,
  dropped acknowledged-purchase responses across refresh, and visible server/browser
  storage failures without a successful-save indicator.
- Local validation: 875 unit tests, 18 focused authority/storage/store tests, seven
  production-build browser flows, typecheck, lint and build passed. The Blueprint
  passes Render’s current JSON schema using the installed Ajv/YAML libraries.
- Production hosting/restart verification and final test results are recorded below
  after deployment. Physical-device/network competition checks remain MP-05.
